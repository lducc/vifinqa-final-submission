## Current state

The table-retrieval CPU stage is complete. It builds one full candidate pool
for all 1,012 questions from:

1. report-gated BM25 rows;
2. Qwen3-Embedding-4B tables restricted to the same ticker/year/scope triple;
3. deterministic statement-to-note edges.

One zero-shot Qwen3-Reranker-8B run scores that union. Sparse, hybrid, and
hybrid+graph rankings are then derived from the same score bytes, so their only
difference is candidate membership. The next action is GPU scoring on a T4;
there is no further CPU retrieval feature to add first.

The ready-to-upload artifact is
`output/final_20260825_canonical/pairs_hybrid_graph.jsonl`. The earlier
`output/final_20260825` directory is superseded: its candidate order depended on
Python set iteration. It is retained only as experiment history.

Public reference before this arm: table F2 `0.5299`, precision `0.3466`, recall
`0.6270`, documents F2 `0.9711`. This is a reference, not a local acceptance
score. The internal labels do not reliably order close retrieval variants.

## Architecture and ownership

```text
question
  -> existing document gate
  -> sparse top 50 + same-triple dense top 40
  -> equal reciprocal-rank first stage
  -> typed note-edge additions (additive, max 3)
  -> Qwen3 reranker once over the full union
  -> RRF with model rank
  -> existing report-aware table budget
  -> existing CSV/query/answer package path
```

The graph is deliberately small. `SOURCE_TABLE` connects rows back to their
statement table and `NOTE_REF` follows a filing's own Thuyết minh reference.
In the current hybrid pool every new graph candidate is a `NOTE_REF`; all
`SOURCE_TABLE` targets were already present. This is typed evidence expansion,
not GraphRAG and not an LLM walk.

| component | responsibility |
|---|---|
| `src/vifinqa/retrieval.py` | report/table extraction, BM25 rows, hierarchy paths |
| `src/vifinqa/rerank.py` | one source-derived table representation |
| `src/vifinqa/fusion.py` | sparse/dense/model reciprocal-rank fusion |
| `src/vifinqa/slots.py` | named line items from the corpus-derived lexicon |
| `src/vifinqa/notes.py` | Mã số and Thuyết minh parsing |
| `src/vifinqa/graph.py` | evidence slots and typed one/two-hop edges |
| `scripts/export_rerank_pairs.py` | sparse+dense union with same-triple policy |
| `scripts/add_graph_tables.py` | additive graph expansion and trace |
| `kaggle/rerank_qwen_8b.py` | resumable T4 scoring and run manifest |
| `scripts/apply_rerank_scores.py` | derive all ranking arms from one score set |

Do not edit `src/vifinqa/answers.py` as part of retrieval work. Another owner is
changing execution and answer binding. `run.py` currently contains changes from
both areas; packaging integration must be committed with that owner rather than
hiding answer changes inside a retrieval commit.

## Rebuild the CPU pool

Prerequisites are the organizer corpus under `data/raw/vifinqa`, the project
virtual environment, and `output/dense`. The dense index itself is generated by
`kaggle/embed_tables.py`; it is not committed because it is hundreds of MB.

Use a new output directory. The entrypoint refuses to overwrite a non-empty one:

```bash
scripts/build_final_candidates.sh output/final_YYYYMMDD_run1
```

That command runs all tests, rebuilds `data/derived/line_items.json` from raw
reports, validates the dense vectors, exports the full pool, adds graph edges,
merges sidecars, and writes `candidate_manifest.json`. A valid current build has:

- 1,012 questions;
- 71,975 candidate pairs;
- 38,497 dense memberships;
- 224 traced graph candidates over 138 questions;
- no duplicate candidate, same-triple violation, or untraced graph target.

The manifest hashes the pairs, sidecars, question file, dense manifest, line-item
lexicon, and every source module that produces candidates. Do not score a pool
whose validator fails.

Two full builds with `PYTHONHASHSEED=3` and `PYTHONHASHSEED=4` produced identical
bytes after deterministic tie-breaking was added:

| artifact | SHA-256 |
|---|---|
| `pairs_hybrid_graph.jsonl` | `c4c0e8da2380ea74a66189b976848a92ad37aee7d4728136f71e77954c5a0a4b` |
| `extra_tables.json` | `9c6994a9a53507efe68de8a2d53c5bcafd0937e40158f8b9c73bb6c7ebd14bb8` |

## Score the full pool on T4

Upload `pairs_hybrid_graph.jsonl` and `kaggle/rerank_qwen_8b.py`. A smoke shard
may verify memory and throughput, but no submission may use partial scores.

For one T4, use the pinned 8B model with `QUANTIZATION="int8"`. If the run needs
multiple sessions, keep each output shard separate and list all completed shard
paths in `RESUME_PATHS` before the next session. Each completed session writes
`scores.jsonl.manifest.json`. For two T4s, 8B fp16 with `device_map="auto"` is
the preferred faster arm. The 4B fp16 fallback has its own pinned revision and
is a different, historically weaker model arm.

```bash
python kaggle/rerank_qwen_8b.py \
  /kaggle/input/vifinqa-final/pairs_hybrid_graph.jsonl \
  /kaggle/working/scores_part1.jsonl
```

After downloading every shard, repeat `--scores` and `--manifest` in matching
order. This rejects missing candidates, mixed prompts/models/quantisation, and
wrong pair or score hashes:

```bash
.venv/bin/python scripts/validate_rerank_scores.py \
  --pairs output/final_run/pairs_hybrid_graph.jsonl \
  --scores output/final_run/scores_part1.jsonl \
  --manifest output/final_run/scores_part1.jsonl.manifest.json
```

## After scores return

Follow sections 6–8 of `docs/final-stretch-plan-20260825.md` exactly:

1. derive `ZS-S`, `ZS-H`, and `ZS-HG` from the same score shards;
2. build and validate all three full 1,012-question packages;
3. submit in that order, changing one variable each time;
4. add the proven note-link append only to the winning parent (`WIN-N`);
5. preserve every package, score manifest, candidate manifest, and SHA-256.

Decision rules are simple: if sparse zero-shot does not beat `0.5299`, diagnose
the fresh representation/scorer; if hybrid loses to sparse, dense does not ship;
if graph loses to hybrid, graph remains trace-only. Do not tune weights or depth
on the public set. Dense depth 41–100 is allowed only as the preregistered
extension after depth 40 wins, using the completed score set as `SKIP_PATH`.

## Explicitly deferred

- coverage filtering or a new table cap;
- unrestricted dense or a dense-only submission;
- LLM query decomposition, GraphRAG, knowledge-graph infrastructure;
- the failed reranker LoRA and its synthetic questions;
- answer/execution changes owned by the other workstream.

These are deferred because they either change more than one variable, failed
earlier evidence, or cannot be judged by the biased internal table labels. The
final stretch is score, validate, submit, and keep only the winning mechanism.
